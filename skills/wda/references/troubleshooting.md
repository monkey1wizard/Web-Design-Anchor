# troubleshooting（Error 的回報與處理）

## 載入時機

只在 `wda check` 或 `wda build` 回報 Error 時載入本檔。除此之外不載入。

## 本檔只做一件事

規定收到 Error 時要怎麼回報、怎麼處理，才不會漏掉關鍵資訊或誤判狀態。**診斷碼與訊息文字本身不在本檔**，那些的唯一宣告來源是 `src/codes.rs`；本檔不重複、不改寫、不舉例任何一筆診斷碼或訊息內容。權威來源：`docs/architecture.md` §2.8 診斷與嚴重度。

## 動作（依序執行）

1. **完整讀出 stderr，不得只看 exit code。** Error 一定出現在 stderr；exit code 只用來判斷「有沒有 Error」，不能取代讀取內容。
2. **逐字回報收到的診斷內容，不得摘要、改寫或省略欄位。** 每一筆診斷都帶有診斷碼、訊息與（適用時的）專案相對路徑與行列位置；這些欄位要原樣轉交給使用者，不得只講「有錯誤」而不附上實際內容，也不得自行編造內容之外的說法。
3. **逐字診斷之後補上翻譯，不取代原文。** 明確說明「發生了什麼」、「影響什麼」、「接下來會做什麼」以及「是否需要使用者決定」；只翻譯這次收到的內容，不自行補寫診斷碼或訊息。權威來源：`docs/architecture.md` §2.8。
4. **將處理路徑分成三條：我可以修、需要你決定、需要工程師。** 「我可以修」表示可依診斷內容與 next action 直接處理；「需要你決定」表示有多個合理方向、範圍或接受風險需要使用者裁定；「需要工程師」表示超出本次處理邊界，轉交 WDA repo 的 plan 或 issue，並附上完整診斷、翻譯與已嘗試的處理方式。權威來源：`docs/architecture.md` §2.8。
5. **依訊息內建的 next action 行動，不得跳過訊息自行判斷該怎麼修。** 訊息與 next action 保證存在且可理解，逐字內容可能隨版本演進；照當次收到的內容行動，不要套用舊版或記憶中的說法。
6. **有 Error 時不得視為可以繼續 build 或部署。** Error 代表 build / project correctness 會被影響，這是阻擋條件，不是可忽略的提示。
7. **處理後重新執行同一指令，確認 Error 已清除。** 不得只憑修改內容判斷「應該修好了」，必須讓 `wda` 再跑一次同一個指令驗證。
8. **重新執行後仍回報同一顆 Error，或改動看似無效時，把完整診斷內容連同已嘗試的處理方式一起交給使用者，不得自行重試到收斂為止。** 這是判斷邊界之外的情況，路由給使用者裁定。權威來源：`docs/architecture.md` §2.8。

## 邊界

本檔不解讀任何具體診斷碼或訊息文字的意義，也不列舉分類、範例或修法對照表；那些內容一旦寫進本檔就會與 `src/codes.rs` 重複宣告。本檔也不判斷「這個情況算不算 Error」，那是 `wda` 本身依 severity 規則決定的結果，本檔只處理「已經收到 Error 之後」要做什麼。Warning 的回報義務不在本檔，路由到 `references/reporting.md`。
