# Skill仕様

この文書はCoreのSkill層に関する契約である。Skillは`skills/wda/`ディレクトリに置く。この文書はSkillの内容を繰り返さず、Skillに含めてよいものと含めてはならないもの、および適用される受け入れ基準だけを定める。

## 役割と責任の境界

SkillはAIの操作手引きおよびワークフロー層である。`wda`の認識とインストール方法、プロジェクト構造の読み方、各コマンドを呼び出す時点、プロジェクトの変更方法、プロジェクト文書の保守方法をAIに案内する。

Skillは仕様の情報源ではない。Coreの規則の複製を保持せず、第二のジェネレーターにもならない。規則はプロジェクト文書とCoreにのみ存在する。Coreと`wda.json`の契約は、WDAを操作する主体がSkillだけであることを前提にしてはならない。

二つの層の責任は、**ワークフロー手順はSkillに、品質基準はプロジェクト文書に置く**という原則で分ける。ブランドや視覚スタイルについて何をどの順序で尋ねるかは手順なのでSkillに属する。視覚品質の基準は品質基準なので、プロジェクトの`docs/design.md`に定める。

## WDAが単一のSkillを維持する理由

### 分割の基準はトリガーを見分けられるかどうか

CLIは呼び出し側が明確な意図を示した後に選択されたコマンドを実行する。誤ったコマンドを選んだ場合、システムは直ちにエラーを返す。AIは意味に基づいてSkillを選び、選択時点では正確な意図を把握していないことがある。誤ったSkillを選んでもエラーは返らず、誤ったワークフローに従う可能性がある。このため、「責任が異なれば新しいコマンドを作る」という規則はSkillには当てはまらない。AIがSkillを読み込む前に、曖昧さなく読み込む一つを選べる場合に限り、Skillを二つに分割できる。

### 評価して却下した三つの分割案

| 分割案 | 却下理由 |
| :--- | :--- |
| CLIコマンドごと | 一つのユーザー依頼が複数コマンドにまたがる場合があり、`deps`コマンドはDesignerが単独で使うことが少ない |
| Designerの作業段階ごと | 各段階のトリガーの意味が大きく重複する。すべてのSkillが同じ規則を繰り返すと、第二のジェネレーターの種になる |
| ユーザーの役割ごと | Engineer用の別Skillを作ると、EngineerもWDAの操作にSkillを必要とすることを認めることになる |

したがって、プロジェクトは`wda`という名前の単一Skillを維持する。

## ディレクトリとファイル構成

### ディレクトリとファイルの配置

```text
skills/wda/
├── SKILL.md
└── references/
    ├── install.md          wdaがPATH上にない場合
    ├── intake.md           新規プロジェクト作成前、または大きなスタイル変更前
    ├── assets.md           Designerがアセットを提供した場合
    ├── reversibility.md    最初の視覚変更前、または変更の取り消し依頼時
    ├── iteration.md        すべての視覚変更前に毎回読み込む
    ├── reporting.md        報告義務が発生した場合
    └── troubleshooting.md  checkまたはbuildがErrorを報告した場合
```

`scripts/`と`assets/`ディレクトリを作成してはならない。

### 配置標準

ディレクトリ配置は[Agent Plugins 1.0.0公開標準](https://agent-plugins.org/specification)に従う。`skills/<name>/SKILL.md`という検出規則は同標準とClaude Codeの両方がサポートする。リリースパッケージのルートには、`$schema`と`name`フィールドのみを含む最小限の`plugin.json`を置く。パッケージ全体が標準のパッケージ仕様に適合するため、互換クライアントは直接インストールできる。インストールはAIホストの責任であり、使用する仕組みはこれだけである。Core独自のインストールコマンドは不要である。

### SKILL.mdの内容許可リスト

`SKILL.md`に含めてよい内容は次の六種類のみである。それ以外は違反となる。

1. 役割と境界の宣言
2. バージョン比較の実行手順
3. 判断の振り分け表
4. ワークフローの停止条件
5. 報告と宣言の義務
6. 権威ある情報源へのポインター（authority pointer）

`SKILL.md`に仕様規則そのものを含めてはならない。

規範マーカーを含む規則をSkill内の文で述べる場合、同じ段落に権威ある情報源へのポインターを置く。規範マーカーは`SKILL.md`フロントマターの`metadata.language`値によって決まる。`metadata.language: en`の場合のマーカーは、must、must not、never、onlyである。`metadata.language: zh-TW`の場合のマーカーは、必須、不得、只能である。

### 行数上限とレビューしきい値

上限は500行または5,000トークンである。レビュー開始のしきい値は300行である。300行を超えてもビルド失敗にはならないが、仕様規則をSkillへ複製していないかを確認するアーキテクチャレビューが必要となる。四つのコマンドと七つの参照文書への案内は300行以内に収める。

## 所有とリリース

エンティティ、仕様、コピーの責任分担は次のとおりである。

| 項目 | 所有する層 |
| :--- | :--- |
| Skillの内容 | `src/`と`docs/`の隣にある`skills/wda/`。`docs/`の中には置かない |
| Skill仕様 | この文書と関連ADR |
| インストール済みコピー | デプロイされたコピー。PATH上のバイナリと同じ扱いで、別の所有者はいない |

CoreはSkillを生成し、各リリースに同梱する。SkillをAIホストへインストールするのはホストの責任である。この目的で`wda skill`コマンドを追加してはならない。

## バージョン管理

### バージョン番号はリリースと一致する

Skillは独自のバージョン番号を持たない。WDAリリースと同じバージョンを使い、フロントマターの`metadata.version`に記録する。プロジェクトはSkillとCLIの互換性マトリクスを管理しない。

### 三分岐の取り扱い方針

実際のリスクはインストール済みコピーのずれである。SkillのコピーはAIホストにあり、バイナリはPATH上にあり、両者は別々に更新できる。

| 比較結果 | 対応 |
| :--- | :--- |
| 一致 | ワークフローを続ける |
| Skillの方が古い | Warningを報告して続行する。CLIには後方互換性があるため、Skillは新機能を使えないだけである |
| Skillの方が新しい | Errorを報告し、直ちに停止してCLIの更新をユーザーに伝える。AIはベストエフォートのロールプレイへ黙って格下げしてはならない |

比較手順では`SKILL.md`フロントマターの`metadata.version`を読み、`wda --version`の出力テキストと比較する。AIは文字列を直接読み、ホストが意味に基づいてフロントマターフィールドを解析することに依存しない。このため、AIホスト実装間の差異は比較に影響しない。

### SkillはwdaVersionを解釈してはならない

Skillはプロジェクト形式の互換性を判断するために`wda.json`の`wdaVersion`を読んではならない。互換性検査はCoreだけの責任である。Skillが行ってよいのは、`wda check`の診断出力を忠実に伝えることだけであり、第二のバリデーターを作ってはならない。

## 実行スクリプトの禁止

`scripts/`ディレクトリを作成してはならない。

### 追加ランタイムを必要としない前提との衝突

CLIをRustで作る主な理由の一つは、WDAを実行するためにNode.js環境をインストール、管理する必要がないことである。Skillスクリプトで使える言語はAIホストによって異なる。PythonやNode.jsのスクリプトはいずれもランタイム要件を復活させる。ユーザーは`wda`をインストールすれば十分だと思う一方で、実際にはインタープリターも必要になる。

### レッドラインの基準

正しく実行されなければならない処理は`wda`バイナリに属し、新しいコマンドに値するかをプロジェクトが評価する。判断、翻訳、選択が必要な処理はAIに属し、`SKILL.md`に記録する。第三の曖昧な分類はない。スクリプトの主な利点は決定性だが、その根拠は機能をCoreへ移すことを支持する。追加スクリプトを書く理由にはならない。Skillスクリプトが決定的な要件を担うと、コマンド名、副作用契約、バージョン互換性保証を持たないCore機能が追加される。

### 例外手順

スクリプト追加の提案には、言語ランタイムを追加しないという前提を満たす証拠、Coreの責任ではないことを示す十分な根拠、専用ADR、記録されたアーキテクトレビューの承認が必要である。

## ホスト間の移植性

### フロントマターで許可するフィールドは五つ

許可されるのは`name`、`description`、`compatibility`、`metadata`、`license`のみである。`allowed-tools`フィールドは禁止する。これは実験的なプロパティであり、AIホストによるサポートに差がある。これに依存するとSkillが一つの実装に結び付く。

### 唯一の機能前提

Skillがホストに求める機能は一つだけである。ホストはネイティブバイナリを実行し、stdout、stderr、終了ステータスを正しく取得できる。これは`wda check`と`wda build`を確実に実行するために必要なプロセス契約と同じである。Skillは特定ホスト専用のAPIを追加しない。終了ステータスが0でもWarningが存在する可能性がある場合はstderrを読む必要がある。終了コード0またはstdoutだけから実行成功と判断してはならない。

## 外部Skillへの依存禁止

| 振る舞い | 判断 |
| :--- | :--- |
| 特定の外部Skillがないとワークフローを完了できない | 不可 |
| 特定の外部Skillを推奨として名指しする | 不可。外部Skillの名前はいつでも変わり、機能しなくなる可能性がある。名前を指定するとWDAが一つのベンダーのエコシステムに結び付く |
| ホスト環境に連携可能な他のSkillが存在する | 可。WDA Skillはそれらの存在を透過的に扱い、干渉しない |

## Skillの検出とインストール案内

`wda.json`が存在しない場合、ユーザーがWDAのインストールまたはセットアップ、新規WDAプロジェクトの作成を明示的に依頼したときに限り、プロジェクト作成前にSkillを検出する。WDAプロジェクト外での一般的なWebサイト開発依頼ではSkillを読み込んではならない。AIがWDAプロジェクト内に入った後もSkillの対象範囲は変わらない。SkillがインストールされていないAIは公式READMEの案内に従う。Skillが利用可能だと推測してはならない。

Skillにインストールコマンドを再掲してはならない。`wda`のインストール、またはPATH上に`wda`がない場合の対応が必要なら、既存の`references/install.md`を参照し、その案内に従う。

READMEは各プラットフォーム向けのインストールコマンドを管理する。Skillとこの文書はプラットフォーム固有のコマンドを複製してはならない。

Skillに実行スクリプトを含めてはならない。`scripts/`ディレクトリを作成してはならない。この制限はSkillと参照文書の両方に適用する。

「バージョン管理」節ではSkillのバージョンとCLIの扱いを定める。検出またはインストールのフローによって、この扱いは変わらない。

## 四段階の受け入れ基準

| 段階 | 内容と基準 | 実行方法 |
| :--- | :--- | :--- |
| L1 仕様準拠 | `tests/skill.rs`が`SKILL.md`フロントマターのすべてのキーが許可された五フィールドのいずれかであることを検査する | ブロッキングCIゲート |
| L2 境界保護（ガードレール） | Skillの文面に`src/codes.rs`の診断コード値がリテラルで含まれないことを確認する | 回帰を防ぐブロッキングCIゲート |
| L3 動作評価 | プロンプト質問バンクに対してテキスト照合を行う。この方法ではトリガー不足を測定できず、ADR-06は既知の不足として記載する | テキスト照合評価 |
| L4 削除テスト | Skill全体を削除した後、人がCoreとプロジェクト文書だけでWDAを正しく操作できるかを確認する | 手動テスト。未実施 |

SkillをリリースできるかはL3評価で決める。SkillをCIフローに入れられるかはL1とL2で決める。L2に完全合格しても、L3が目標を満たさなければSkillをリリースしてはならない。

`assets/`作成を禁じるL2の規則は、WDA固有のアーキテクチャ規則であり、一般標準ではない。プロジェクトファイルを生成するのは`wda init`の責任である。Skillがプロジェクトファイルへコピーできるテンプレートを持つと、`init`と競合する第二の生成元になる。

現在L3はトリガー不足を検査できない。AIが使うべきSkillを読み込まない場合がある。そのときAIは一般的なWeb開発知識でプロジェクトファイルを編集し、`wda check`と`wda build`を省略し、警告も出さない可能性がある。そのため`description`フィールドの作成と評価は、別個の中核課題である。
